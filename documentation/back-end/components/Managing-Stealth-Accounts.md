# Managing Stealth Accounts in Wallet

## Deep Research — Stealth Address Wallet Management & Balance Aggregation

## 1. Executive Summary

Managing stealth accounts in a wallet is the critical UX layer that sits between on-chain event indexing (Component 5) and the user-facing interface. The fundamental challenge is that stealth addresses, by design, create a **new unique address per incoming payment** — meaning a single user can quickly accumulate dozens or hundreds of addresses, each holding fractional balances.

Production systems have converged on two primary models:

- **Fluidkey's Unified Dashboard Model:** Stealth addresses are 1/1 Safe smart accounts. The system generates new counterfactual addresses per payment via a server that holds a BIP-32 derived viewing key node. All stealth accounts are aggregated into a single portfolio view, and spending is abstracted so the user interacts as if using a single wallet. The Safe is only deployed at the moment of withdrawal (counterfactual instantiation).

- **Umbra's Withdrawal-Based Model:** Stealth addresses are standard EOAs. Users scan announcement events with their viewing key, discover payments, and individually withdraw funds to a safe destination address. The UI presents a list of received payments with per-address withdrawal actions.

For an Account Abstraction (AA) backend like Openfort, the Fluidkey model is more aligned because it already uses smart accounts (Safe) and abstracts the multi-address complexity away from the user. The key architectural decisions involve: how to store and index stealth accounts locally, how to query balances across potentially hundreds of addresses efficiently, how to enable spending from fragmented balances, and how to do all of this without leaking privacy.

## 2. The Core Challenge: Many Addresses, One Wallet

### Why This Is Hard

Traditional wallets operate on a one-address-per-chain model. A user has a single Ethereum address and all tokens arrive at that address. Stealth addresses invert this: every incoming payment generates a unique, never-before-seen address. This creates several cascading problems:

**Address Proliferation:**
A user receiving 10 payments has 10 separate stealth addresses. Each may hold different tokens in different amounts on different chains. The wallet needs to track, index, and aggregate all of them.

**Fragmented Balances:**
If a user has $1,000 total but it's spread across 10 stealth addresses ($100 each), spending $500 requires combining funds from 5 addresses. Most DeFi applications connect to a single wallet address and cannot natively handle multi-address spending.

**Discovery vs Display:**
The wallet must continuously scan for new announcements (Component 5 feeds into this) and surface new addresses as they are discovered — but it must present them in a way that doesn't overwhelm the user.

**Key Derivation Per Address:**
Every stealth address has a unique stealth private key. The wallet must either derive this key on-demand (from the spending key + ephemeral public key) or cache derived keys securely. This adds computational overhead and security surface.

### The Two Approaches in Production

| Dimension | Fluidkey (Dashboard) | Umbra (Withdrawal) |
|-----------|---------------------|--------------------|
| Address type | 1/1 Safe smart accounts | Standard EOAs |
| User sees | Single aggregated balance | List of individual payments |
| Spending | System finds best combination of addresses | User withdraws per-address to chosen destination |
| Key delegation | Viewing key node shared with server | Fully client-side scanning |
| Address generation | Server generates via BIP-32 derivation | Sender generates via ECDH |
| Smart contract deploy | Counterfactual until withdrawal | No contract (EOA) |
| Discovery speed | Instant (server knows addresses) | Slow (client scans events) |

## 3. Production Model Comparison: Umbra vs Fluidkey

### Architectural Divergence

While both systems implement the stealth address concept from ERC-5564, their wallet management approaches are fundamentally different.

**Umbra** follows the pure ERC-5564 model closely:
1. Sender generates stealth address via ECDH using recipient's public keys
2. Sender calls `announce()` on ERC5564Announcer, emitting the ephemeral public key
3. Recipient scans all `Announcement` events, uses viewing key to identify their payments
4. Recipient derives the stealth private key and withdraws to a chosen address

The wallet's job is to manage a list of "received stealth payments" — each has a status (unclaimed, withdrawn), an amount, a token type, and the ability to export the private key or trigger a withdrawal.

**Fluidkey** deviates significantly:
1. The stealth address is not generated by the sender — it's generated by Fluidkey's server using the recipient's BIP-32 derived viewing key node
2. When someone resolves `username.fkey.eth`, the ENS offchain resolver returns a **new** stealth Safe address every time
3. The sender simply sends to the resolved address — no stealth-aware wallet needed
4. Fluidkey's server knows all generated addresses (since it generated them) and notifies the user
5. The Safe contract is predicted via CREATE2 but only deployed when funds are spent

This means Fluidkey bypasses the announcement scanning entirely. The trade-off is that Fluidkey's server can see all incoming transactions and balances (via the shared viewing key node), but it can never spend funds (the spending key never leaves the client).

### Why This Matters for Wallet Management

For **Umbra**, the wallet management layer needs:
- An announcement scanner/indexer
- Per-address key derivation capability
- A withdrawal flow (potentially via relayer for gas-free withdrawals)
- Simple list-based UI showing individual payments

For **Fluidkey**, the wallet management layer needs:
- A backend that generates and tracks stealth addresses (via BIP-32 derivation)
- A balance aggregator that queries all known stealth addresses
- A spending optimizer that selects which addresses to spend from
- Smart account deployment logic (counterfactual → deployed)
- A unified dashboard UI

## 4. Fluidkey: Unified Dashboard Model (Deep Dive)

### Architecture Overview

Fluidkey's wallet management is built on several interconnected components:

#### 4.1 Key Generation and Delegation

When a user signs into Fluidkey, they sign a key generation message with their existing Ethereum wallet. The signature is used to deterministically derive:
- A **private spending key** (never leaves the client, never shared)
- A **private viewing key** (a BIP-32 node is shared with Fluidkey's server)

The private key pair is NOT stored locally. Every time the user opens the app and wants to spend, they must re-sign the key generation message to re-derive their keys. This is a critical security decision: there's no persistent key storage on-device.

The shared viewing key node follows the path: `m/5564'/N'` where `N` is currently `0` for all users. The Fluidkey technical docs note that in the future, `N` may reference specific time periods or dimensions, enabling granular view access delegation to third parties.

**SDK Functions:**
```typescript
// From @fluidkey/stealth-account-kit

generateKeysFromSignature(signature: Hex): {
  spendingPrivateKey: Hex;
  viewingPrivateKey: Hex;
  spendingPublicKey: Hex;
  viewingPublicKey: Hex;
}

extractViewingPrivateKeyNode(
  viewingPrivateKey: Hex
): BIP32Node  // Node at m/5564'/0'
```

#### 4.2 Stealth Address Derivation

Each new stealth address is derived by incrementing a counter on the BIP-32 viewing key node. Each leaf produces an **ephemeral private key**, from which a **stealth EOA** is derived. This stealth EOA becomes the sole owner/signer of a 1/1 Safe smart account.

> **See:** [Creation of Key Pairs](./Creation-Key-Pairs.md), Section 4.2 — "BIP-32 Hierarchical Derivation" for the full derivation path structure (`m/5564'/N'/c0'/c1'/0'/p'/n'`), component breakdown, ENSIP-11 coinType encoding, and multi-chain derivation details.

**SDK Functions:**
```typescript
generateEphemeralPrivateKey(
  viewingKeyNode: BIP32Node,
  nonce: number, // Incrementing counter
  chainId: number
): Hex

generateStealthAddresses(
  ephemeralSecret: Hex,
  spendingPublicKeys: Hex[]
): { stealthAddresses: Address[], viewTags: number[] }
```

#### 4.3 Counterfactual Safe Prediction

The stealth Safe address is predicted using CREATE2 without deploying the contract. The sender sends funds to this predicted address. The Safe is only deployed when the user wants to spend from it.

```typescript
predictStealthSafeAddressWithClient(
  client: PublicClient,
  args: {
    stealthSigner: Address,    // The stealth EOA
    safeVersion: '1.3.0',
    threshold: 1,
    useDefaultAddress: true,
    chainId: number,
  }
): Address  // Predicted Safe address
```

**Key Parameters for Recovery:**
- `safeVersion`: `'1.3.0'`
- `threshold`: `1`
- `useDefaultAddress`: `true`
- `chainId`: `0` (cross-chain)

#### 4.4 Unified Dashboard Architecture

Fluidkey's dashboard aggregates all stealth accounts into a single view:

The user sees a single, aggregated portfolio. They never interact with individual stealth addresses directly unless they choose to via the Labels feature.

#### 4.5 Spending Logic

When the user initiates a send:
1. Fluidkey checks all stealth addresses for sufficient single-address balance
2. If no single address has enough, it finds the optimal combination
3. The Safe contract is deployed (if counterfactual) and funds are consolidated
4. The transaction appears to the recipient as a single payment

Gas is deducted from the token itself (e.g., USDC), so the user doesn't need native ETH in any stealth address. This is made possible by the Safe smart account architecture and gas sponsorship.

## 5. Umbra: Withdrawal-Based Model (Deep Dive)

### Architecture Overview

Umbra's wallet management is simpler at the wallet level but pushes more complexity to the user.

#### 5.1 Scanning and Discovery

The receiver's wallet scans all `Announcement` events from the ERC5564Announcer contract using the ViewTag optimization, which eliminates ~99.6% of announcements before performing full ECDH derivation.

> **See:** [Event Listener](./Event-Listener.md), Section 3 — "The ViewTag Optimization" for the full scanning algorithm, performance benchmarks, and implementation details.

#### 5.2 Account Data Model

Each discovered stealth payment is tracked as a discrete entity:

```typescript
interface UmbraStealthPayment {
  stealthAddress: Address;
  ephemeralPublicKey: Hex;
  amount: bigint;
  tokenAddress: Address; // 0xEeee...eE for ETH
  txHash: Hex;
  blockNumber: number;
  timestamp: number;
  status: 'unclaimed' | 'withdrawn';
  withdrawTxHash?: Hex;
  withdrawAddress?: Address;
}
```

#### 5.3 Withdrawal Flow

Umbra handles ETH and tokens differently:

**ETH Transfers:**
ETH is sent directly to the stealth address. The recipient derives the stealth private key, imports it into a wallet, and sends a standard transfer. This requires the stealth address to have gas, which the sender typically provides by sending slightly more than the intended amount.

**ERC-20 Token Transfers:**
Tokens are held in the Umbra contract itself. The recipient calls `withdraw()` on the contract from the stealth address to claim tokens. Gas is covered by:
- Pre-funding the stealth address with ETH
- Using a Gas Station Network (GSN) relayer — Umbra swaps some tokens via Uniswap to pay the relayer
- Meta-transaction signed by the stealth private key

#### 5.4 UI Model

Umbra's UI is a flat list of received payments:

```
┌──────────────────────────────────────────────────────┐
│                  Umbra Receive Page                  │
├──────────────────────────────────────────────────────┤
│  Scanning... ████████░░░░ 72% (Block 19,234,567)     │
│                                                      │
│  ┌────────────────────────────────────────────────┐  │
│  │ 1.0 ETH    │ 0xab...cd │ Unclaimed │ [Withdraw]│  │
│  │ 500 USDC   │ 0xef...12 │ Withdrawn │ ✓         │  │
│  │ 0.5 ETH    │ 0x34...56 │ Unclaimed │ [Withdraw]│  │
│  └────────────────────────────────────────────────┘  │
│                                                      │
│  Advanced: [Export Private Key] [Set Block Range]    │
│                                                      │
└──────────────────────────────────────────────────────┘
```

**Key UX features:**
- Scanning progress indicator (this can take minutes for full history)
- Per-payment withdrawal action
- Privacy warnings when withdrawing to an address with ENS, POAPs, etc.
- Advanced mode: export stealth private key, set scan block range

## 7. Address Lifecycle Management

Every stealth address goes through a lifecycle from discovery to archival. Properly tracking this lifecycle is essential for both UX and privacy.

### 7.1 Lifecycle States

```
                ┌──────────┐
                │ PREDICTED│  (Fluidkey: counterfactual Safe generated)
                └─────┬────┘
                      │ Funds arrive
                      ▼
                ┌──────────┐
                │  FUNDED  │  (Has balance, contract undeployed for Fluidkey)
                └─────┬────┘
                      │ User initiates spend
                      ▼
                ┌──────────┐
                │ DEPLOYED │  (Fluidkey: Safe contract deployed on-chain)
                └─────┬────┘
                      │ Funds partially spent
                      ▼
                ┌──────────────┐
                │ PARTIAL_SPENT│  (Some balance remains)
                └──────┬───────┘
                       │ All funds spent
                       ▼
                ┌──────────┐
                │  SPENT   │  (Zero balance, all funds withdrawn)
                └─────┬────┘
                      │ After confirmation period
                      ▼
                ┌──────────┐
                │ ARCHIVED │  (Historical record only)
                └──────────┘
```

### 7.2 State Transitions

```typescript
enum StealthAccountStatus {
  PREDICTED = 'predicted',     // Address predicted but not yet funded
  FUNDED = 'funded',           // Has received funds, contract may not be deployed
  DEPLOYED = 'deployed',       // Smart account deployed on-chain
  PARTIAL_SPENT = 'partial',   // Some funds withdrawn, some remain
  SPENT = 'spent',             // All funds withdrawn
  ARCHIVED = 'archived',       // Historical record only
}

interface StatusTransition {
  from: StealthAccountStatus;
  to: StealthAccountStatus;
  trigger: string;
  timestamp: number;
  txHash?: Hex;
}
```

### 7.3 Transition Logic

```typescript
function computeStatus(
  account: StealthAccount,
  currentBalance: bigint
): StealthAccountStatus {
  if (currentBalance === 0n) {
    if (account.totalReceived === 0n) return 'predicted';
    if (account.totalSpent > 0n) return 'spent';
    return 'spent'; // Received and fully spent
  }
  if (account.isDeployed && account.totalSpent > 0n) return 'partial';
  if (account.isDeployed) return 'deployed';
  return 'funded';
}
```

### 7.4 Archival Policy

Archived addresses should be retained indefinitely for:
- Tax reporting and audit trails
- Transaction history export
- Potential late-arriving token transfers (airdrops, delayed settlements)
- Recovery scenarios where the user needs to reconstruct history

### 8.5 Aggregated View (Materialized)

```sql
-- Materialized view for fast portfolio queries
CREATE MATERIALIZED VIEW user_portfolio AS
SELECT
    sa.user_id,
    sb.token_address,
    sb.token_symbol,
    sb.token_decimals,
    SUM(sb.balance_raw) as total_balance_raw,
    SUM(sb.balance_usd) as total_balance_usd,
    COUNT(sa.id) as address_count,
    COUNT(sa.id) FILTER (WHERE sa.status = 'funded') as funded_count,
    MAX(sb.last_updated) as last_updated
FROM stealth_accounts sa
JOIN stealth_balances sb ON sb.stealth_account_id = sa.id
WHERE sa.status IN ('funded', 'deployed', 'partial')
  AND sb.balance_raw > 0
GROUP BY sa.user_id, sb.token_address, sb.token_symbol, sb.token_decimals;

CREATE UNIQUE INDEX idx_portfolio ON user_portfolio(user_id, token_address);

-- Refresh periodically
REFRESH MATERIALIZED VIEW CONCURRENTLY user_portfolio;
```

## 9. Balance Aggregation Strategies

### 9.1 The Challenge

A user with 50 stealth addresses needs balance checks for each address, for each token they care about. Naively, this is `50 addresses × N tokens = 50N` individual RPC calls — which is both slow and expensive.

### 9.2 Strategy 1: Multicall3 Batch Queries

Multicall3 (`0xcA11bde05977b3631167028862bE2a173976CA11`) is deployed on 100+ chains at the same address and can aggregate multiple `balanceOf` calls into a single RPC request.

> **See:** [Balance Aggregation](./Balance-Aggregation.md), Sections 3–4 — for the full Multicall3 implementation including ERC-20 batch queries via Viem multicall, native ETH via `getEthBalance`, batch size limits (50–100 calls per batch), chunking strategies, and consistency guarantees.

### 9.3 Strategy 2: Native ETH via Multicall3 getEthBalance

> **See:** [Balance Aggregation](./Balance-Aggregation.md), Section 4 — for the `getEthBalance` implementation and native ETH batching pattern.

### 9.4 Strategy 3: Indexer API (Alchemy/Moralis/Covalent)

Instead of querying the chain directly, use portfolio APIs that track balances natively:

```typescript
// Alchemy: getTokenBalances for multiple addresses
// Note: Most APIs limit batch size to 1-5 addresses per call

async function indexerBalanceQuery(
  addresses: Address[]
): Promise<TokenBalance[]> {
  const results = await Promise.all(
    addresses.map(addr =>
      fetch(`https://eth-mainnet.g.alchemy.com/v2/${API_KEY}`, {
        method: 'POST',
        body: JSON.stringify({
          method: 'alchemy_getTokenBalances',
          params: [addr, 'erc20'],
        }),
      }).then(r => r.json())
    )
  );
  return aggregateResults(results);
}
```

**Trade-offs:**
- Faster than on-chain multicall for token discovery (finds unknown tokens)
- Rate-limited by API provider
- May have slight delay vs on-chain state
- Privacy concern: API provider sees all your stealth addresses

### 9.5 Strategy 4: Hybrid (Recommended)

```
┌───────────────────────────────────────────────┐
│            Balance Aggregation Pipeline       │
├───────────────────────────────────────────────┤
│                                               │
│  1. Known Tokens (from announcement metadata) │
│     → Multicall3 batch balanceOf              │
│     → Fast, on-chain, no API dependency       │
│                                               │
│  2. Unknown Token Discovery (periodic)        │
│     → Indexer API (Alchemy/Moralis)           │
│     → Discovers airdrops, unexpected tokens   │
│     → Fluidkey's "Import" feature             │
│                                               │
│  3. Native ETH                                │
│     → Multicall3 getEthBalance                │
│     → Always checked                          │
│                                               │
│  4. Cache Layer                               │
│     → Store in stealth_balances table         │
│     → Refresh on new block / user action      │
│     → Materialized view for portfolio         │
│                                               │
└───────────────────────────────────────────────┘
```

## 10. Multi-Chain Address Tracking

### 10.1 Cross-Chain Address Validity

Both Fluidkey and the ERC-5564 standard support cross-chain stealth addresses:

- **Fluidkey** uses `chainId: 0` in its derivation path, meaning generated stealth addresses are valid across all EVM chains
- **ERC-5564** stealth meta-addresses use EIP-3770 chain prefixes (`st:eth:`, `st:oeth:`, etc.) but the underlying addresses are chain-agnostic
- **Announcements** are chain-specific (emitted on the chain where the transfer occurs)
- **CREATE2 Safe addresses** are deterministic across all chains with the same factory

### 10.2 Multi-Chain Tracking Schema

```sql
-- Chain-specific balance snapshots
CREATE TABLE chain_balances (
    id                  SERIAL PRIMARY KEY,
    stealth_account_id  INTEGER REFERENCES stealth_accounts(id),
    chain_id            INTEGER NOT NULL,
    token_address       VARCHAR(42) NOT NULL,
    balance_raw         DECIMAL(78,0) NOT NULL DEFAULT 0,
    last_block          INTEGER,
    last_updated        TIMESTAMP,

    UNIQUE(stealth_account_id, chain_id, token_address)
);

-- Track which chains have been scanned for each address
CREATE TABLE chain_scan_status (
    stealth_account_id  INTEGER REFERENCES stealth_accounts(id),
    chain_id            INTEGER NOT NULL,
    last_scanned_block  INTEGER NOT NULL DEFAULT 0,
```

## 11. Privacy-Preserving UI/UX Patterns

### 11.1 Fundamental Privacy Rules

**NEVER display:**
- Full list of stealth addresses to unauthorized viewers
- Links between stealth addresses and the user's primary address
- Patterns that could reveal address clustering (e.g., timestamps of address generation)

**ALWAYS provide:**
- Aggregated totals rather than per-address breakdowns by default
- Privacy warnings before withdrawal to known addresses
- Plausible deniability — any single stealth address could belong to anyone

### 11.2 Fluidkey's UX Patterns

> For the full Fluidkey architecture (BIP-32 derivation, server-side scanning, Safe smart accounts), see Section 4.

**New Address Per Payment:**
Each time someone resolves `username.fkey.eth`, a new stealth address is returned. The user shares this ENS name as their payment identifier. From the user's perspective, they have one "address" (their ENS) but infinite receiving addresses.

**Labels Feature:**
Fluidkey allows categorizing stealth accounts with labels (e.g., "personal", "freelance", "savings"). When sending, users can choose which label's addresses to spend from, adding a layer of organizational privacy.

**Import Feature:**
By default, Fluidkey tracks ETH, USDC, and DAI. Users can use the "Import" feature to add visibility for other tokens. This prevents unnecessary token discovery queries that could reveal address patterns.

**Transaction Export:**
For tax and accounting, Fluidkey provides a one-click export of all transactions. This is critical because users cannot easily reconstruct their full history from block explorers alone (since addresses are unlinkable).

### 11.3 Umbra's UX Patterns

**Withdrawal Warnings:**
Before withdrawal, Umbra checks if the destination address:
- Owns an ENS name
- Holds POAP NFTs
- Has other publicly identifiable on-chain activity

If any are detected, a warning is displayed: withdrawing to a publicly linked address destroys the privacy benefit.

**Scanning UX:**
Umbra displays a progress bar during announcement scanning. Since full history scans can take minutes, this is critical for user trust. Users can also set custom start/end blocks to limit scan range.

**Private Key Export:**
Advanced users can export the stealth private key for each received payment, allowing them to import it into MetaMask or another wallet for manual management. This is a power-user feature with explicit warnings.

## 12. Fund Consolidation and Spending Logic

### 12.1 The Consolidation Problem

When a user wants to send $500 but their largest single stealth address holds $200, the wallet must combine funds from multiple addresses. This is one of the hardest UX and privacy challenges.

### 12.2 Fluidkey's Approach

Fluidkey handles this transparently:

1. User initiates a send of $500 USDC
2. Backend searches for the optimal combination of stealth addresses
3. For each selected address, the counterfactual Safe is deployed (if not already)
4. Funds are consolidated and sent in a single transaction from the user's perspective
5. Gas is paid from the token itself (no need for native ETH in stealth addresses)

**Optimization Algorithm (Conceptual):**

```typescript
function findOptimalAddresses(
  targetAmount: bigint,
  availableAddresses: { address: Address; balance: bigint }[]
): Address[] {
  // Sort by balance descending (greedy approach)
  const sorted = [...availableAddresses]
    .filter(a => a.balance > 0n)
    .sort((a, b) => Number(b.balance - a.balance));

  // First: check if any single address covers the amount
  const single = sorted.find(a => a.balance >= targetAmount);
  if (single) return [single.address];

  // Second: greedy selection of largest addresses
  const selected: Address[] = [];
  let remaining = targetAmount;

  for (const addr of sorted) {
    if (remaining <= 0n) break;
    selected.push(addr.address);
    remaining -= addr.balance;
  }

  if (remaining > 0n) throw new Error('Insufficient total balance');
  return selected;
}
```

**Privacy Considerations:**
- Consolidating multiple stealth addresses in a single transaction reveals they belong to the same user (on-chain clustering)
- Fluidkey mitigates this by using the Safe's batch execution — all actions happen within the Safe contracts
- The recipient only sees one incoming transfer, not the consolidation mechanics

### 12.3 Batched Execution via Smart Account

For AA-based systems, consolidation can be done via UserOperation batch calls:

```typescript
interface ConsolidationPlan {
  sourceAddresses: Address[];        // Stealth addresses to spend from
  amounts: bigint[];                 // Amount from each
  tokenAddress: Address;
  destinationAddress: Address;
  totalAmount: bigint;
  estimatedGas: bigint;
}

// Execute via ERC-4337 UserOperation
async function executeConsolidation(plan: ConsolidationPlan) {
  const calls = plan.sourceAddresses.map((addr, i) => ({
    target: plan.tokenAddress,
    value: 0n,
    data: encodeFunctionData({
      abi: erc20Abi,
      functionName: 'transfer',
      args: [plan.destinationAddress, plan.amounts[i]],
    }),
  }));

  // Batch all transfers in a single UserOperation
  const userOp = await buildBatchUserOp(calls);
  return await bundler.sendUserOperation(userOp);
}
```

## 13. Wallet Recovery and Replay

### 13.1 Fluidkey Recovery Model

Fluidkey's recovery is deterministic because all stealth addresses are derived from the viewing key via BIP-32. The process iterates through derivation indices, predicts Safe addresses via CREATE2, and checks balances until a gap limit of consecutive empty addresses is reached.

> **See:** [Stealth Private Key Recovery & Wallet Injection](./Stealth-Private-Key-Recovery-Wallet-Injection.md), Section 5 — for the full Fluidkey recovery flow, BIP-32 key hierarchy, `recoverAllAccounts` implementation, counterfactual Safe address prediction, and SARA recovery tool.

**Gap limit comparison (wallet-management-specific):**

| Approach | Gap Limit | Rationale |
|----------|-----------|-----------|
| Fluidkey | 20 consecutive empty indices | BIP-32 sequential derivation |
| Umbra | All announcements scanned | No sequential order to exploit |
| Custom | Configurable per user | Power users may want deeper scans |

### 13.2 Umbra Recovery Model

Umbra recovery requires scanning all historical announcements:

1. User signs the key generation message → derives spending + viewing keys
2. Fetch all `Announcement` events from the ERC5564Announcer contract since deployment
3. For each announcement, perform the view tag check + full ECDH check
4. Matched announcements represent discovered stealth payments
5. For each match, derive the stealth private key and check on-chain balance

This is slower than Fluidkey's approach because it requires scanning all announcements on all chains. View tags reduce the computational cost but scanning bandwidth remains a bottleneck.

```typescript
async function processNewAnnouncement(
  announcement: IndexedAnnouncement,
  userKeys: { viewingPrivateKey: Hex; spendingPublicKey: Hex }
): Promise<ManagedStealthAccount | null> {

  // Step 1: View tag pre-filter (from Component 5)
  // Already done by indexer — only matching announcements arrive here

  // Step 2: Full ECDH verification
  const isForUser = checkStealthAddress({
    ephemeralPublicKey: announcement.ephemeralPublicKey,
    spendingPublicKey: userKeys.spendingPublicKey,
    userStealthAddress: announcement.stealthAddress,
    viewingPrivateKey: userKeys.viewingPrivateKey,
    viewTag: announcement.viewTag,
    schemeId: VALID_SCHEME_ID.SCHEME_ID_1,
  });

  if (!isForUser) return null;

  // Step 3: Parse metadata for token info
  const tokenInfo = parseAnnouncementMetadata(announcement.metadata);

  // Step 4: Create managed account record
  const account: ManagedStealthAccount = {
    stealthAddress: announcement.stealthAddress,
    status: 'funded',
    balances: [{
      tokenAddress: tokenInfo.tokenAddress,
      balance: tokenInfo.amount,
    }],
    labels: [],
    chainId: announcement.chainId,
    announcement,
  };

  // Step 5: Persist to database
  await db.stealthAccounts.create(account);

  // Step 6: Trigger balance verification (on-chain confirmation)
  await verifyBalanceOnChain(account);

  return account;
}
```
